# Historical report — superseded by the current README and handover

The reduction examples mentioned below were intentionally removed. Do not restore them.

**Assessment: useful as a compact DirectX experiment archive, but the compute examples need correctness repairs before serving as dependable starting points.** The single-file design and executable-size focus are deliberate and appropriate for the stated demoscene purpose. The most important problems are reproducible shader failures, incomplete initialization, and fragile build settings.

Reviewed September 12, 2026 at local commit `ba11402` (May 4, 2016). The repository contains 14 Visual Studio projects: 12 DirectX 11 examples and two DirectX 12 examples. There are 17 C files and 23 HLSL files, including snippets and an alternative triangle implementation. This evaluation covers the current local checkout, rather than a proposed change or historical diff.

All builds and diagnostic edits were performed in copies under this evaluation directory. The original repository was left unchanged; its existing modification to `DirectX 12/02_Triangle/Compression.log` was preserved.

**Verified findings, in priority order**

1. **P1 — Reduction examples 02–09 omit necessary synchronization.** The last six reduction steps read shared values written by other threads, with no barrier between steps. This assumes execution behavior that does not hold across Direct3D 11 implementations. On WARP, all eight examples returned approximately **0.3125 instead of 1.0** for an all-white input. The baseline example 01 passed. Inserting unconditional `GroupMemoryBarrierWithGroupSync()` calls after these steps in diagnostic copies repaired all three fixtures for examples 02–08. Keep barriers in the Shader Model 5 implementation; any architecture-specific shortcut needs an explicit, validated constraint. Representative location: [example 02 shader, line 66](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/04_DirectCompute Parallel Reduction Case Study/02_ParallelReduction/ParallelReduction.hlsl:66>). Microsoft documents the [group synchronization contract](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/groupmemorybarrierwithgroupsync).

2. **P1 — Constant buffers contain unwritten shader inputs.** The Julia, color-filter, and reduction demos map a dynamic constant buffer with `D3D11_MAP_WRITE_DISCARD`, then write only the rotation matrix diagonal. The color-filter demo also leaves `ColorAdd` and `Contrast` unwritten. The HLSL consumes these fields, so rendering can depend on undefined values: distorted rays, incorrect colors, or missing geometry. Initialize all shader-consumed fields on every map, preferably by copying a complete initialized CPU structure. Static storage for the mapped pointer does not initialize the pointed-to GPU allocation. Locations: [map operation](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/03_DirectCompute PostFX Color Filters/Window.c:382>), [partial matrix](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/03_DirectCompute PostFX Color Filters/Window.c:402>), [unwritten filter fields](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/03_DirectCompute PostFX Color Filters/Window.c:423>). Microsoft explicitly states that [WRITE_DISCARD makes previous contents undefined](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_map). This finding is established by code and the API contract; a visible rendering failure was not tested.

3. **P1 — Release compute demos require optional debug components and continue after initialization failure.** Eleven DirectX 11 compute examples pass `D3D11_CREATE_DEVICE_DEBUG` unconditionally, including Release. A machine without the debug layer can fail device creation; the code ignores that failure and immediately dereferences the swap chain. Make the debug flag conditional and stop cleanly on a failed creation call. The DirectX 12 debug path similarly dereferences an unchecked debug interface, while `ThrowIfFailed` merely displays a message in Debug and does nothing in Release. Locations: [DirectX 11 device creation](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/03_DirectCompute PostFX Color Filters/Window.c:224>), [DirectX 12 error helper](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 12/02_Triangle/Window.c:113>), [debug interface](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 12/02_Triangle/Window.c:207>). The debug layer is an [optional component](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-devices-layers). This failure path was not simulated on a machine lacking that component.

4. **P2 — Reduction example 09 reads the wrong second row.** Each thread starts at `(DTid.x * 8, DTid.y * 2)`, but its second eight samples use `idx + 8` through `idx + 15`. That overlaps the next thread's horizontal samples instead of reading the next image row. After fixing synchronization alone, alternating black/white rows still produced **0 instead of 0.5** for the first output tile. Changing the second group to `idx + c_width` through `idx + c_width + 7` repaired both remaining fixtures. Location: [second sample group, line 66](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/04_DirectCompute Parallel Reduction Case Study/09_ParallelReduction/ParallelReduction.hlsl:66>).

5. **P2 — The declared DirectX 12 x64 configurations cannot compile the active entry point.** Both projects expose x64 configurations while compiling `__declspec(naked)` and x86 inline assembly. Both Debug and Release x64 builds fail with C2485/C4235 after retargeting. The triangle also has incompatible custom `memcpy` details for x64. Either implement and configure an ordinary x64 entry point or remove unsupported targets. Location: [triangle entry point](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 12/02_Triangle/Window.c:175>). Microsoft confirms that [naked functions are unavailable on x64](https://learn.microsoft.com/en-us/cpp/cpp/naked-cpp?view=msvc-170).

6. **P2 — Build settings are tied to old installations.** Projects use `v120` or `v140`; several explicitly require Windows SDK `10.0.10240.0`. Hard-coded library directories remain even when the SDK property is overridden. Retargeting alone therefore leaves the DirectX 12 skeleton unable to find `d3d12.lib`, as well as the triangle Debug build. The compressed-build scripts likewise embed SDK paths and depend on an already-built object. Use inherited SDK library properties and document an exact supported compiler/SDK combination plus separate ordinary and compressed build steps. Locations: [skeleton library path](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 12/01_Skeleton/GraphicsDemo.vcxproj:80>), [compressed build script](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 12/02_Triangle/BuildSmall.bat:1>). The old toolchains were unavailable, so compatibility with their original configurations was not established.

7. **P2 — Reduction dispatch truncates the image bottom.** At the supplied 1920×1080 dimensions, the Julia dispatch uses `1080 / 16`, rendering only 1072 rows. Example 09's reduction uses `1080 / 128`, covering only 1024 rows. Other reduction tile sizes also truncate the tail. Supporting full-image reduction requires ceiling division, bounds checks, neutral contributions from invalid lanes, and a valid-pixel divisor for edge tiles. All group threads must still reach synchronization calls. Locations: [Julia dispatch](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/04_DirectCompute Parallel Reduction Case Study/09_ParallelReduction/Window.c:440>), [reduction dispatch](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/04_DirectCompute Parallel Reduction Case Study/09_ParallelReduction/Window.c:459>). The numerical fixtures use exact tile multiples and do not validate edge handling.

8. **P2 — The last color-filter pixel uses an uninitialized result.** `idx < (c_width * c_height - 1)` excludes the final valid pixel, but the shader still writes `Color` afterward. FXC reports X4000 in the Debug shader compilation. Use the full valid range and ensure every written pixel has a defined color. Location: [color-filter bounds condition](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/03_DirectCompute PostFX Color Filters/ColorFilters.hlsl:72>).

9. **P2 — Animation uses total elapsed time as its per-frame increment.** `dt = CurrentTime / 20000.0f` is added to interpolation state on every frame. Animation therefore speeds up over the run and varies with frame rate, contrary to the `dt` comment. Use the difference between consecutive timestamps. Location: [time update](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/03_DirectCompute PostFX Color Filters/Window.c:372>).

Two smaller teaching traps deserve correction: [the first reduction shader](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/04_DirectCompute Parallel Reduction Case Study/01_ParallelReduction/ParallelReduction.hlsl:67>) tests misspelled `OPTMIZATION`, so changing the defined `OPTIMIZATION` flag does not select the intended branch; [GetUniform](<C:/Code/GitHub/graphicsdemoskeleton/DirectX 11/02_DirectCompute Julia4D/Window.c:68>) never produces the negative values promised by its `(-1, 1)` comment. Its random generator also freezes one of the original generator's state components.

**Design and maintenance judgment**

The strongest aspect is transparency: startup, resources, shaders, and submission are visible with little framework machinery. Embedded compiled shader bytecode fits the executable-size objective, and the staged compute examples make optimization ideas easy to compare. The DirectX 12 frame wait and upload-heap vertex data are explicitly explained simplicity choices; changing those is lower priority than correcting wrong results.

The repository has no checked-in automated correctness suite, CI configuration, or runnable GPU benchmark harness. The reduction examples change tile sizes and do not supply measurements establishing that successive versions are faster. Repeated scaffolding has propagated initialization, timing, and error-handling issues across projects. Documentation lacks a build matrix, output expectations, and clear descriptions of each reduction stage. Generated executables, an object file, logs, and a Visual Studio database are tracked, which makes a clean build harder to distinguish from historical output.

Recommended order: repair shader synchronization/indexing and buffer initialization; make startup failures explicit and debug components optional; establish a reproducible Win32 build and resolve or remove x64 targets; retain numerical tests and add edge-tile cases; document examples and measure GPU time before presenting an optimization ranking. The single-file structure can remain intact throughout.
